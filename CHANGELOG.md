# Changelog

Notable changes to this repo, kept for future-me/future-agent context. Newest first.

## Unreleased

- **One geometry output per element kind, not per (kind, shape) — schema change.** `topic.json`'s
  `"geometry": { "way": ["line", ...] }` (a list, letting a kind declare multiple shapes) is now
  `"geometry_output": { "way": "line" }` (one shape, or omit the kind entirely) — every shipped
  config only ever declared one shape per kind anyway. The routing-graph flag is now a fully
  separate, orthogonal `"graph": { "way": true, "node": true }` field (it always was independent of
  shape — a topic can still want both a routing table and a rendered line for the same ways) —
  `GeometryShape::Graph` is gone, `GeometryShape` is just `Point`/`Line`/`Polygon` now.
  - **Output tables collapse from up to 6 per topic to 3.** `{table}_geom`/`_point`/`_polygon` and
    the `_relation_*` variants are replaced by `{table}_node_geom`/`{table}_way_geom`/
    `{table}_relation_geom` — one self-describing table per *kind* (`osm_id, geom_type, geom,
    length_m`; `geom_type` is `Point`/`LineString`/`MultiLineString`/`Polygon`), covering whichever
    shape that kind's topics actually declared. New `geom::rows::GeomRow` replaces `WayRow`/
    `PointRow`/`PolygonRow`. Applies to every output backend (`pg`/`csv`/`geojson`/`geojsonseq`) —
    Postgres tables use a generic `geometry(Geometry, 3857)` column instead of a fixed subtype.
  - **This was the fix for the last CSV/GeoJSON alignment gap.** `{table}_point.csv` used to mix
    node-point rows (written during the select phase, in node order) and way-point rows (written
    during materialize, in way order) in one file — the one geometry table `geojson.rs`'s
    forward-cursor join (see the previous three entries below) couldn't safely use, since the two
    row groups aren't in the tag file's own row order relative to each other. Splitting node and
    way geometry into physically separate tables removes the mixing entirely: `geojson.rs` now uses
    the same `OrderedGeomCursor` for node/way/relation geometry alike, no `HashMap` left except
    `edges.csv` (relation path needs random access by member-way id) and the way-graph-fallback
    (unexercised by any shipped config).
  - `geom::plan::GeometryPlan` simplified accordingly: `way_line_topics`/`way_polygon_topics`/
    `point_topics`/`way_point_eligible`/`node_point_eligible`/`relation_line_topics`/
    `relation_point_topics`/`relation_polygon_topics` (9 fields, 3 separate topic-index lists per
    kind plus eligibility bools to disambiguate the shared point table) collapse to
    `node_geom_topics`/`way_geom_topics`+`way_shape`/`relation_geom_topics`+`relation_shape` (a
    topic-index list plus a parallel declared-shape array per kind) — possible only because a kind
    now has at most one shape, so there's nothing left to disambiguate.
  - Verified byte-identical CSV/GeoJSON/GeoJSONSeq output against the pre-change build on
    `berlin.osm.pbf` (`tilda`, `trains`, `live_raw` configs) and on `brandenburg-latest.osm.pbf`
    (`tilda`); alignment re-verified end to end (tag-row `osm_id` sequence vs. geometry-table
    `osm_id` sequence, deduped for side-split) on all three. No measurable RSS/time regression on
    the same Brandenburg `/usr/bin/time -v` benchmark used for the earlier alignment work.
  - Migrated all 8 shipped configs' `topic.json` to the new schema; updated
    `editor/lib/liveEditor.ts`'s SQL (queries `{table}_way_geom`/`{table}_node_geom` now, was
    `{table}_geom`/`{table}_point`) and `README.md`'s data-model section to match.

- **Live editor: start page + per-topic dropdown, and each topic now runs as if it were its own config.** Previously the editor auto-picked the first config on load and showed every topic in it as an accordion, and every edit re-ran the pipeline against the *whole* multi-topic config (so editing `bikelanes` also paid for classifying `roads`, `tilda`'s other topic, on every save).
  - `/` is now a start page (`app/page.tsx`, a server component) listing every `configs/*` dir; picking one goes to `/editor/<config>` (`app/editor/[config]/page.tsx`, new dynamic route), which shows a topic dropdown instead of the old accordion — current topic lives in `?topic=` so refresh/back/shared links preserve it.
  - `lib/liveEditor.ts`: dropped the auto-pick-first-config fallback (`ensureConfigSelected`) in favor of explicit `requireConfig()`/`requireTopicDir()` guards (409 if unset — a start page is now mandatory, not optional). New `switchTopic(topic)` builds a scratch dir containing *only* that topic's subdirectory plus the config's shared root-level files (`macros.json`/`sanitizers.json`/`producers.json`/`units.json`/`value_sets.json` — matched by "is a file, not a directory," not a hardcoded name list) and points every pipeline/`tree_json` call at it — confirmed against `TopicRunner::load_all`/`src/paths.rs` that a config-dir with exactly one topic subdirectory works identically to one with many, so this needed zero Rust changes. New `POST /api/topic-select` route.
  - `components/App.tsx` → `components/LiveEditor.tsx`: now takes `config`/`topics`/`topic`/`onTopicChange` as props (the URL-owning page drives selection) instead of self-fetching `/api/configs`/`/api/topics` and rendering a multi-topic accordion — `hiddenTopics`/`expandedTopics`/`categoriesByTopic` (per-topic Sets/Records) all collapse to single-topic equivalents since there's never more than one topic in view now.
  - Verified via the running container: config/topic selection, topic-mismatch rejection (switching topics now 400s a stale request for the old one), category CRUD, all four `DagView` tabs, and the way-search feature all round-trip correctly against the new topic-scoped pipeline dir.
- **Live editor: standalone "Sanitizers" tab** — lists a topic's named sanitizers (shared config-root `sanitizers.json` merged with the topic's own, topic-local winning — same merge `TopicRunner::load` does internally via `load_topic_sanitizers`) and plots one's mapping/replace/builtin chain at a time, independent of which `Extract` leaf (if any) happens to reference it. Previously a sanitize chain was only visible as a tail hanging off one specific field's Producer tree in the "Producer" tab — there was no way to see "what does `traffic_sign` do" without first finding a field that uses it.
  - `src/tree.rs`: new `sanitizer_dag(name, chain)` — same `DagNode`/`DagEdge` JSON shape `producer_dag` already emits (root labeled by name, each step feeding the next top-down), so the editor's `DagView` component needed no new rendering code.
  - `src/bin/tree_json.rs`: new `sanitizer` mode (`list` / `<name>`), handled *before* `TopicRunner::load` — it only needs `load_topic_sanitizers`, not a fully-compiled topic (categories/producers/transforms), so listing/plotting sanitizers stays cheap and works independent of whether the rest of the topic currently compiles.
  - `editor/lib/liveEditor.ts` + new `editor/app/api/sanitizer-dag/[topic]/route.ts`, `editor/components/DagView.tsx`/`App.tsx` gained a fourth mode/tab alongside Producer/Categorize/Decision tree — reuses the existing single-level list→graph fetch flow (`deriver`/`decision-tree`'s pattern), not the two-level `category` one.
- **Live editor migrated from Vite (a plugin-as-backend hack) to Next.js (App Router) + TypeScript.** Groundwork for the tool growing past a single-page dev utility (a real start page, multi-page navigation, background export services) — file-based routing and route handlers give that room; the old approach was one `vite.config.ts` middleware function accreting every endpoint.
  - `editor/lib/liveEditor.ts` now holds all the server-side logic (config/topic file I/O, `psql`/pipeline subprocess calls) that used to live directly in `vite.config.ts`; `editor/app/api/**/route.ts` is one route handler per endpoint, same URL shapes as before (`/api/bounds`, `/api/extract`, `/api/configs`, `/api/config`, `/api/topics`, `/api/dag/:topic` + its two siblings, `/api/categories/:topic`, `/api/category/:topic/:kind/:name`, `/api/classify`, `/api/topic/:topic`) — the frontend needed no changes.
  - **Bug caught during migration:** `lib/liveEditor.ts`'s mutable state (current bbox/config) started out as plain module-level `let`s, exactly like the old single-file Vite plugin. Next.js compiles each `route.ts` into its own module graph, so `/api/config`'s write and `/api/topics`' read silently landed on *different* variable instances — switching configs appeared to succeed but the topics list never changed. Fixed by pinning the state object to `globalThis` (the same pattern Next.js docs recommend for a singleton Prisma client, for the same underlying reason) — worth remembering for any future server-side module state in this app.
  - `editor/components/{App,Map,Editor,DagView}.tsx` (moved from `editor/src/`) are unchanged apart from a `"use client"` directive each (all touch the DOM/browser APIs directly — MapLibre, CodeMirror, `@xyflow/react`).
  - `editor/index.html`/`vite.config.ts`/`src/main.tsx` removed; replaced by `app/layout.tsx` + `app/page.tsx`. `package.json` scripts now `next dev -p 5173`/`next build`/`next start -p 5173` — same port, so `docker-compose.yml` needed no port changes.
  - Root `Dockerfile` (standalone one-container demo, no `db` service) is now stale on top of the earlier Postgres-source migration — see BACKLOG.
- **Live editor reads bbox selections from Postgres instead of `osmium extract` + full PBF reparse per edit** (see BACKLOG's now-resolved entry on this). New flow:
  - A one-time "all ways" pass (`osmnexus <region>.osm.pbf --config-dir configs/live_raw --output pg --create-index`, new `configs/live_raw/topic.json`: `"accept_all": {"way": true}`, `"outputs": true`, way `"line"` geometry) loads every way's tags + linestring geometry for a whole region into `live_raw`/`live_raw_geom`, GiST-indexed. Needed no new ingest code — `accept_all`/`"outputs": true` already existed in `topic::spec::{AcceptAllSpec, OutputsSpec}`, just unused by any shipped config until now.
  - New `src/live_source.rs` + `Config::source`/`--bbox`/`--source-table` (`src/config.rs`): `--source postgis` reads ways intersecting `--bbox` straight out of `{source_table}`/`{source_table}_geom` (one `ST_Intersects` query) and runs them through the same `TopicRunner::process`/`TableWriters::route_tag`/`route_way` the PBF path uses — no PBF decode, no node-coordinate resolution (the geometry's already known; `ST_AsEWKB`/`ST_Length` hand back exactly the `WayRow` shape `route_way` expects). Deliberately way-line-only for now — no routing graph, relations, or node topics.
  - `editor/vite.config.ts`: `/api/extract` no longer shells out to `osmium extract`, just records the bbox; `runPipeline` now invokes `osmnexus --source postgis --bbox ... --source-table live_raw` instead of a PBF path. `/api/bounds`' base-extent query moved from `osmium fileinfo` to a `psql` `ST_Extent` query against `live_raw_geom`.
  - `editor/docker-compose.yml` gained a `db` (`postgis/postgis:16-3.4`) service + `PG*` env wiring; `editor/Dockerfile` installs `postgresql-client` for the bounds query.
- **Pass B peak memory cut ~20% (germany-latest, `configs/tilda`, 4 threads, CSV: 15366 → 12211 MB peak RSS)** — three independent fixes to state the select phase was holding for no reason. Wall time unchanged within noise (this machine's run-to-run spread is wide enough that no speed claim is made).
  - `SelectionContext::use_counts` is no longer returned. It had zero consumers outside `osm::reader` — `collect_coords`/the fallback node scan read it for the `shared` flag, `log_node_summary` for its counters, all before the context is constructed — yet it stayed resident through the entire materialize phase at ~29 B per referenced node. `NodeCoords`' doc had claimed for a while that folding `shared` in "lets `use_counts` be dropped after Pass B"; nothing actually dropped it. Both paths now do, explicitly.
  - `collect_coords` folds node blobs into the map in chunks of 256 (`FOLD_CHUNK_BLOBS`) rather than `collect()`ing every blob's `Vec` before folding any of them, which used to put the whole file's node data in memory twice.
  - The coordinate map is pre-sized (`with_capacity_and_hasher`) instead of grown from empty. **This was the largest of the three** — the final doubling of a country-scale hashbrown table holds the old and new bucket arrays at once, a ~1.5× transient worth GBs. Brandenburg 1080 → 976 MB from this line alone.
  - Note on the capacity hint: it's an upper bound (a referenced node may be absent from the file), and hashbrown rounds to `next_pow2(hint × 8/7)`, so a big enough overshoot would double the table permanently instead of saving the transient. Checked against an `osmium extract -s simple` extract (dangling refs by construction): still a win, 158 → 152 MB.
  - Verified output-identical (sorted — row order is already nondeterministic run-to-run, since way rows are routed straight from a rayon `par_iter`) on berlin + brandenburg × `configs/tilda` and berlin × `configs/trains`, the latter covering the relation-geometry and node-point paths, each via both the sorted fast path and `PBF_FORCE_FALLBACK=1`.
  - Measurement note for future work: **`--features dhat` is not usable on this pipeline at any real scale** — it could not finish berlin (normally ~9 s) in 10 minutes, and spent 25+ minutes inside Pass A on brandenburg; the tag-classification allocation volume swamps its bookkeeping. Use `/usr/bin/time -v` peak RSS instead. Conveniently, the germany baseline measures 15366 MB RSS against the 14.86 GB heap figure recorded for `790c02a02`, i.e. at this working-set size the mmapped PBF pages get reclaimed rather than inflating RSS.
- Live editor visualizes routing-graph cut points: `editor/vite.config.ts` `buildFeatureCollection` now keeps *all* edge segments per `osm_id` (it used to keep only the last one, silently dropping segments of ways split at intersections) and emits a second `cutPoints` FeatureCollection — the shared node between consecutive segments of the same way, i.e. where the graph broke a way apart. Rendered as small orange dots (`editor/src/Map.tsx`, `CUT_POINTS_SOURCE_ID`), fed from `editor/src/App.tsx`'s new `cutPoints` state.
- Live editor now starts on a bundled `example` topic (`editor/live-config/example/`, matching `highway=cycleway`) instead of hardcoded `bikelanes_simple/way/bikeway`. The right-hand panel is minimizable (▶/◀ toggle) and lists all categories under the topic (`GET /api/categories/:topic`, scans `way/`/`node`/`relation` dirs), with a text input + "+" to add a new category (writes a blank `{"condition":{}}` file via the existing classify endpoint and reruns the pipeline).
- Live editor (`editor/`) generalized from a single hardcoded fixture to arbitrary areas:
  - `editor/docker-compose.yml` now mounts a configurable base `.osm.pbf` via `BASE_PBF` (defaults to `../berlin.osm.pbf`) at `/data/base.osm.pbf`, passed to the dev server as `BASE_PBF_PATH`.
  - `editor/Dockerfile` installs `osmium-tool`.
  - `editor/vite.config.ts`: added `POST /api/extract` which runs `osmium extract -s complete_ways` against the base PBF for a user-picked bbox and switches the live editor to that extract; `GET /api/bounds` now returns the base file's full extent (via `osmium fileinfo -e -j`) until an extract is picked, then the extract's bounds plus `selected: true`.
  - Frontend (`editor/src/Map.tsx`, `editor/src/App.tsx`): shift+drag on the map draws a bbox and calls `/api/extract`; a banner prompts selection until one is made.
  - Fixed a latent bug found while wiring this up: the editor was invoking a stale `osm-pipeline` binary and reading a `geometries.csv` file that no longer exist — the current pipeline binary is `osmnexus` and it writes `edges.csv` (see `src/output/rows.rs` `EDGE_TABLE`/`GEOM_COLUMNS`). Updated `PIPELINE_BIN` and the CSV filename read in `buildFeatureCollection` accordingly.
